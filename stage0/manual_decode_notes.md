## 一、实验记录（客观数据，已填）

### 环境

| 项 | 值 |
| --- | --- |
| GPU | NVIDIA GPU |
| torch / transformers | 2.12.1+cu129 / 5.12.1 |
| 模型 | Qwen3-0.6B，bf16，权重占显存约 1.11 GB |
| 模型结构 | 28 层，16 个注意力头，8 个 KV 头（GQA），head_dim 128，词表 151936 |

### 关键形状

| 张量 | 形状 | 含义 |
| --- | --- | --- |
| `input_ids` | `[1, 21]` | batch 1 条，prompt 21 个 token |
| `logits`（默认） | `[1, 21, 151936]` | 每个位置对词表每个词的打分 |
| `logits`（`logits_to_keep=1`） | `[1, 1, 151936]` | 只保留最后一个位置，省掉 95.2% |

### forward 耗时 vs 序列长度（各测 10 次取平均）

| 序列长度 | forward 耗时 | 每 token |
| ---: | ---: | ---: |
| 16 | 23.28 ms | 1.4549 ms |
| 64 | 18.35 ms | 0.2868 ms |
| 256 | 14.92 ms | 0.0583 ms |
| 512 | 15.70 ms | 0.0307 ms |
| 1024 | 23.71 ms | 0.0232 ms |
| 2048 | 44.40 ms | 0.0217 ms |
| 4096 | 105.08 ms | 0.0257 ms |
| 8192 | 275.05 ms | 0.0336 ms |

512 以内基本是水平线，说明瓶颈是固定开销（kernel 启动 + 读 1.1GB 权重），
不是注意力计算。1024 往上才开始爬升，4096→8192 长度翻倍耗时涨 2.6 倍，
体现出注意力的 O(n²)。

### KV Cache 加速比（各生成 32 个 token）

| 上下文长度 | 重算全部 | 用缓存 | 加速比 |
| ---: | ---: | ---: | ---: |
| 128 | 0.47 s | 0.47 s | 1.00x |
| 512 | 0.59 s | 0.49 s | 1.22x |
| 1024 | 0.90 s | 0.48 s | 1.88x |
| 2048 | 1.59 s | 0.53 s | 3.00x |
| 4096 | 3.38 s | 0.57 s | 5.92x |

> 这些数字每次跑都会有百分之十几的波动（桌面程序也在用同一块 GPU）。
> 重要的是趋势——短上下文接近 1x，长上下文显著加速——而不是具体小数。

KV Cache 开销：每 token 112 KB（2 × 28层 × 8个kv头 × 128维 × 2字节）。
8192 上下文一条请求要 896 MB，16GB 卡最多同时装约 17 条。

### 三种实现的一致性

| 对比 | 结果 |
| --- | --- |
| 有缓存手写 vs `generate()` | 33 token 完全一致 |
| 无缓存手写 vs `generate()` | 第 6 步分歧，最终 30 token |

分歧那一步的现场：候选「深度」20.0000，「大」19.8750，差距 0.1250；
而两条数值路径的 logits 最大差异是 0.2500。差距小于误差，翻转是必然的。

## 四、踩坑记录

已经遇到并解决的（保留作参考）：

1. **`eos_token_id` 三处不一致。**
   `config.json` 是 `151645`，tokenizer 是 `151645`，
   但 `generation_config.json` 是列表 `[151645, 151643]`，而后者才是生效的。
   写成 `next_id == generation_config.eos_token_id` 是拿 int 比 list，
   永远为 False，循环停不下来，模型会越过结束符自顾自开始新一轮对话。

2. **裸 prompt 停不下来。**
   Qwen3-0.6B 是指令模型，不套 chat template 就退化成续写机器，
   120 步都不会输出 EOS。必须用 `apply_chat_template`。

3. **耗时曲线和预期相反。**
   原以为序列变长每步会变慢，实测 21→50 反而略降。
   原因是测量尺度不对：这个长度区间被固定开销主导。
   教训是性能结论必须先确认自己测的是不是瓶颈所在的那一段。

4. **KV Cache 在短上下文反而略慢。**
   128 token 时加速比 0.99x。缓存帮不上"读权重"和"启动 kernel"这两件事，
   还额外增加了每层维护缓存的开销。

5. **第一个 decode 步有巨大尖峰（137ms）。**
   预热时只跑了 prefill 形状，decode 的 `[1, 1]` 形状是第一次遇到，
   GPU 要重新挑 kernel。预热必须覆盖所有会用到的形状。
